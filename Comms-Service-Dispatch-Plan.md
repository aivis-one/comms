# Comms Service -- Dispatch / План сборки (Master-chat control plane)

> **Control plane** сборки comms-сервиса и его деплоя: роли, порядок фаз, ЖИВОЙ
> статус, реестр тест-бандов, петля исполнения. **Дизайн** -- в
> `Comms-Service-Architecture.md` (source of truth; на него ссылаются исполнители).
>
> Ведёт Master-chat. Лежит в БЗ (durability, §7).

---

## 0. Роли

- **Master-chat** (этот): код НЕ пишет. Нарезает самодостаточные хэндофферы, принимает
  отчёты, сверяет с `done-when`, ведёт статус, выпускает следующую фазу. Реестр
  тест-бандов -- на нём.
- **Чат-исполнитель:** свежий чат на КАЖДЫЙ хэндоффер, **в отдельном Claude-проекте со
  своей БЗ** (`comms` + `cbshome` + `velo` + оба дока). Отдаёт ТОЛЬКО изменённые файлы.
- **Босс:** применяет файлы в репо, пушит, обновляет БЗ, катит на VPS, **приносит отчёт
  исполнителя обратно в Master-chat**.

**Следствие разделения проектов:** Master-chat НЕ видит БЗ исполнителей -> хэндофферы
обязаны быть самодостаточными, а отчёты приходят через босса.

**Репозитории:** `aivis-one/comms` (сервис), `aivis-one/ops` (деплой-тулкит),
`aivis-one/velo` (клиент №1, product-side glue), `aivis-one/cbshome` (клиент №2, позже).

## 1. Модель исполнения

Строго **линейная, just-in-time**. Параллелизм = **1**. Хэндофферы пишем **по одному** --
реализация фазы может подкрутить следующие. Не торопимся: скорость рождает переделки.

**Ключевое ограничение:** применение + БЗ + раскат -- внешние. Зависимую фазу не выпускаем,
пока предыдущая не применена и не легла в БЗ.

**Приоритет:** comms делается ДЛЯ VELO. cbshome -- донор кода (движок) и валидатор
домен-агностичности, НЕ ведущий заказчик.

Порядок предварительный -- пересматриваем после каждой фазы.

## 3. Петля на каждую фазу

1. **Master-chat** пишет хэндоффер следующей фазы (шаблон §4) -> `HANDOFF ISSUED`.
2. **Босс** вставляет в свежий чат-исполнитель (проект исполнителей).
3. **Исполнитель** тянет из БЗ, делает, отдаёт файлы + отчёт -> `REPORTED`.
4. **Босс:** пушит в `test` -> **смотрит CI** (репо `comms`: галочка/крестик) -> красный:
   правка через исполнителя; зелёный: `velo update` на test-VPS (раскат **comms, затем
   продукт**) -> обновляет БЗ -> приносит отчёт в Master-chat -> `APPLIED+БЗ`.
5. **Master-chat** сверяет с `done-when`. Не сошлось -> корректирующий мини-хэндоффер.
   Сошлось -> `VERIFIED-DONE`, и только теперь пишется следующий хэндоффер.

**Правило:** не выпускать зависимую фазу до `APPLIED+БЗ` предыдущей.

## 4. Шаблон хэндоффера

Отдельный `.md` (files-only), самодостаточный:
- **RULE ZERO** -- забор по скоупу: закрыть ровно перечисленное, не расширять; лишнее -- в отчёт.
- **Рабочие правила** -- чат по-русски, комментарии в коде на английском, `->` и `--`;
  Python 3.12, ORM-only (без SQL); файлы отдавать файлами; **не реконструировать из памяти --
  тянуть из БЗ**; не пушить/коммитить (пушит босс).
- **Целевой репо** + ветка `test` + ссылка на архдок как источник дизайна.
- **Таблица** `# | item | file | goal | how | done-when | status`.
- **Verify & report:** тесты/линт зелёные; по каждому item подтвердить «done-when».
- **Тест-банд** (если добавляет тесты) -- из реестра §5.
- Границы: не залезать в чужой репо/трек.

## 5. Реестр тест-бандов

Банды нужны: `recipient.id` = **product user id** -> id-пространство comms общее с продуктом, а
интеграционные тесты на test-VPS делят БД с VELO.

| Диапазон | Занят | Примечание |
|----------|-------|------------|
| `80000-88999` | **зарезервирован за `comms`** | по 1000 на модуль; конкретный банд выдаётся при выпуске фазы |
| `80000-80999` | comms: engine core (Phase 1) | выдан |
| `81000-88999` | comms: свободно | assign at issue |
| `89000-89999` | **VELO навсегда** (`test_reviews`, `test_master_notifications`) | comms не занимать |

## 6. Гейты качества

1. **CI (лампочка)** на `comms`: pytest (эфемерная БД) + ruff + mypy на каждый push. Красный
   -> на VPS не везём. Без деплоя из CI. Branch protection (шлагбаум) -- позже.
2. **Test-VPS** -- главный гейт: реальная интеграция, реальный Telegram, реальный раскат.
3. **Prod** -- только после зелёного test; мерж `test` -> `main` в обоих репо; БД бэкапится.

## 7. Durability / преемственность

Master-chat теряет контекст. Состояние живёт в БЗ: **архдок + этот док**. Свежий Master-chat
поднимает оба и продолжает. §2 (статус) и §5 (банды) держим актуальными после каждого шага.

**План преемственности:** этот Master-chat ведёт первые фазы; далее -- `Master handoff`
(статус + залоченные решения + что в полёте) новому Master-chat в проекте исполнителей.
