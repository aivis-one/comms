# COMMS x VELO -- product-side integration checklist (Phase 5 scope)

This file documents the EXACT steps on the **product (velo) side** that
make the comms stack reachable. They are applied in the velo repo /
on the VPS by the operator -- the comms repo never touches velo.

Scope guard: this checklist covers **wiring only** (network + env).
The actual integration code -- the `notification_request` relay into
the comms stream, calls to the comms HTTP API, and the user-facing
proxy that sets `recipient_id`/`sender` server-side -- is **Phase 6**,
lives in the velo repo, and is deliberately NOT part of this phase.

---

## 1. Join the shared network (velo `docker-compose.yml`)

The comms stack lives on the external docker network `aivis-shared`
(created idempotently by `comms-deploy.sh install`; `docker network
create aivis-shared` on the velo side first is equally fine -- either
side may create it, the result is identical).

Add the network to velo's compose and attach the backend service to
it (the backend is the only velo service that talks to comms):

```yaml
# --- velo docker-compose.yml ---
services:
  app:
    # ... existing config ...
    networks:
      - default        # keep intra-velo traffic as it is today
      - aivis-shared   # NEW: reach comms-app / comms-redis by name

networks:
  aivis-shared:
    external: true
```

Note: velo's other services (frontend, postgres, redis) do NOT need
`aivis-shared`. Once any service lists an explicit `networks:` key,
compose stops attaching it to `default` implicitly -- hence `default`
is listed explicitly above.

## 2. Accept the comms variables (velo backend `.env`)

Target path (confirmed velo layout): **`/opt/velo/repo/backend/.env`**

The comms deploy body is product-agnostic (DD-8), so it does not know
this path -- it is the VALUE of the `PRODUCT_ENV_PATH` knob in the
comms deploy env (`/opt/comms/.env`, generated by `install` with the
knob EMPTY). For velo, set:

```
# --- /opt/comms/.env ---
PRODUCT_ENV_PATH=/opt/velo/repo/backend/.env
```

With the knob set, `comms-deploy.sh install` writes these three
variables into that file **automatically and idempotently**
(update-in-place if the key exists, append if not). With the knob
empty -- the first run on a fresh VPS, before the env exists to be
edited -- install prints the block for manual paste; alternatively,
set the knob after the first run and re-run `install` (idempotent:
secrets and profile are guarded, only the hand-over re-executes):

```
COMMS_SERVICE_TOKEN=<generated by comms install -- single source>
COMMS_API_URL=http://comms-app:8000
COMMS_REDIS_URL=redis://:<password>@comms-redis:6379/0
```

Semantics:

- `COMMS_SERVICE_TOKEN` -- the shared service token (trust seam,
  DD-6). The velo backend presents it as `Authorization: Bearer
  <token>` on every call to the comms API. Generated ONCE by comms
  install; the comms config and this file carry the same value.
- `COMMS_API_URL` -- the comms API address on `aivis-shared`. The
  comms API is INTERNAL (no host port, no nginx route); this name
  resolves only for containers attached to `aivis-shared`.
- `COMMS_REDIS_URL` -- the durable comms stream backbone, credentials
  included. The Phase 6 relay XADDs `notification_request` entries
  here. Treat this file with the same care as the rest of your
  secrets: the URL carries the redis password.

Restart the velo backend after the variables land.

## 3. What comes next (Phase 6 -- NOT now)

Consumers of the variables above are the integration track in the
velo repo:

- outbox relay: velo -> `notification_request` into the comms stream
  (`COMMS_REDIS_URL`);
- server-to-server calls to the comms HTTP API (`COMMS_API_URL` +
  token);
- the user-facing proxy that sets `recipient_id`/`sender`
  **server-side** (comms authenticates the PRODUCT, not the user --
  the proxy owns user-level authorization);
- the delivery-callback receiver.

None of that is wired by this checklist; this phase only guarantees
that when Phase 6 code lands, the network path and the credentials
are already in place.
